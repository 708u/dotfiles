# claude global rules

## 基本方針

ユーザーの指示や指摘に対してより良い方法がある場合、必ず代替案を提案すること。過度にユーザーに寄り添わず、建設的に批判する。技術的根拠を示した上で反論・提案を行う。

代替案は一文で述べ、依頼された作業はそのまま続ける。判断が分かれて成果物が実質的に変わるときのみ詳述する。

## 作業の進め方

### 依頼範囲の厳守

依頼された範囲のみを変更する。README、アドバイス、構造変更など、依頼されていない成果物を生成・変更しない。範囲を広げる必要があるときは、着手前に確認を取る。

### 可逆な作業は完遂する

調査・計画・複数段階の実装など、巻き戻し可能な作業は途中の確認で区切らず最後まで進める。取り消しが難しい操作は事前に確認を取る。

## 自然言語生成

- 絵文字を利用しないこと
- 不必要な強調表現を控えること
- 根拠を示せない誇張的な形容表現を使わないこと
- 相関関係を因果関係として断言しないこと
  - 因果関係を主張する場合は根拠を示すこと
- 一般語彙として浸透している略語を除き、許可なく単語を省略しないこと (認知コストが上がるため)
- 仕様について文書を書くとき、指示を受けている場合を除き不要な文脈の注釈を入れないこと
  - 悪い例: table設計の文書で、依頼されていない「メンテナンスコストが削減できる」等の利点を箇条書きで添える
- tool 呼び出しの前後の短い進捗も日本語で書くこと
  - 長い session の後半や英語の資料を読んだ直後に英語へ戻りやすい

### 出力の長さ

応答は要点に絞る。留保・前置き・要約の反復で分量を増やさない。説明を求められたときは概要を示し、詳細な解説は明示的に要求されたときのみ書く。

ディスクに書く文書 (レポート、markdown、要約) も必要な内容を満たす長さに留める。定型の節や重複する要約を含めない。

### 文書に含める内容と更新

規則文や設計文書に含める具体例は、変動しにくいドメイン構造に限る。直近のワークアラウンド、進行中の施策の状態、クラス名やファイルパス、ツールの件数、個別の外部事業者の列挙は含めず、「決済事業者との連携」のように構造を表す語で書く。具体名を残すのは db/migrate のように長期に安定したものだけとする。

既存の文書 (Artifact、Asana のタスク本文など) を更新するときは、経緯や日付付きの追記をせず、現在の結論だけが書かれた状態に置き換える。経緯は commit message や更新履歴の欄に残す。

### 語彙の選択

一般的な日本語の会話・文書で使われない語を避ける。数学・物理・英語からの直訳語と、硬い文体に交じる口語動詞が主な対象。以下の置き換えに従う。

適用範囲は生成する文書だけでなく、session 内の応答、commit message、PR description、subagent への指示など、自分が書く日本語の全てとする。

以下の表に含めるのは、形態素解析で絞り込めず textlint が検出できない語だけとする。textlint が検出する語は表に含めない。

直訳・他分野からの借用:

| 避ける語 | 置き換え |
| --- | --- |
| 隔離 (責務分離の意味で) | 分離 |
| 後続 (後任者の意味で) | 後任の担当者 |
| 空白 (欠落・不足の意味で) | 欠落、不足、未記入 |

口語動詞 (文書では硬い側に揃える):

| 避ける語 | 置き換え |
| --- | --- |
| 読む (layout を読む) | 読み込む |

動詞と目的語の組み合わせにも注意する。

- 「成立する」の多用 →「可能になる」
- 「〜が生まれる」(擬人的) →「発生する、追加される」
- 「proto を動かす」→「移動する」(変更と区別する)
- 「最終形を B に置く」→「最終形は B とする」

見出しや区分名に、比喩や直訳で作った造語を使わない。物や図形に例えず、指している内容を直接書く。

- 「権限の行列」→「プランごとの利用可否」

### textlint による AI 語彙の自動チェック

markdown と HTML への Write / Edit 後、PostToolUse hook が textlint を自動実行する。指摘があれば別の表現に言い換えてから完了とする。指摘が無くなるまで繰り返す。Artifact は publish 前にローカルの .html を経由するため、この hook の対象に含まれる。

設定と辞書は `~/.claude/textlint/` に置く。実体は dotfiles の `.config/claude/textlint/` にある。

ユーザーに不自然と指摘された語は、次の手順で `dictionary.json` に登録する。

1. 指摘された表現を kuromojin で形態素解析し、tokens を決める。空白の有無など表記の揺れで区切りが変わるときは、揺れごとに entry を分ける
2. 検出すべき例文と、同じ語の正しい使い方の例文で textlint を実行し、前者がすべて検出され、後者が検出されないことを確かめる
3. 既存の書式に合わせて末尾に追加する。message は「"語" は避ける語です。「置き換え」に言い換えてください。」の形にする

誤検出を避けられない語や、頻度・離れた語の組み合わせ・意味で決まる語は辞書に登録せず、「語彙の選択」の表に追加する。

### 差別用語の禁止

差別的な含意を持つ語を、文章・コメント・識別子・サンプルデータに使わない。中立な語へ置き換える。

代表的な語は textlint の辞書で検出する。branch 名などの固有名と区別できず辞書に登録していない語:

- master → primary

## GitHub操作

### GitHub へのアクセス

GitHub の操作には gh CLI を使う。GitHub MCP は使わない。認証は gh が keyring に保持するトークンを使い、トークンを新規に発行しない。他ツールへ渡す必要があるときは `gh auth token` で取得する。環境変数として export しない。トークンの値を commit 対象のファイルや settings.json に書かない。

### PR作成前のブランチ名確認

ブランチ名が作業内容とずれていたら、PRを作成する前にrenameする。push済みのブランチをPR作成後にrenameすると、旧ブランチの削除で PRが閉じられる。

### PRのdescription

`--body-file` でファイルから渡す。`--body` にヒアドキュメントを埋め込まない。

PR を作成する前に、repository に PR template (`.github/pull_request_template.md` など) があるかを必ず確認する。ある場合は description をその template に沿って書く。見出しの名前と順序を変えず、各見出しのコメントで指示された内容を記入する。該当しない見出しも削除せず、該当しない旨を書く。

編集するときは直前に `gh pr view <number> --json body -q '.body'` で最新版を取得し、他者 (ユーザー、レビュアー、bot) の追記を必ず引き継ぐ。確認なしの上書きは禁止。

PR が存在するブランチへ push したら、description を push 後のブランチの差分に合わせて更新する。レビュー指摘への対応で push したときも同様に更新する。変更内容の節だけでなく、ファイルパス、QA の項目と結果、変更しなかったことの記述も見直す。

`gh pr view --json` に `body` を含めると制御文字でjqのパースが失敗するため、bodyは単独で取得する。

### PR への画像添付

frontend や UI の変更を含む PR では、変更後の画面のスクリーンショットか動画を必ず添付する。画面以外でも、動作確認の結果を QA の証跡として示せるときは添付する。スクリーンショットは Chrome MCP で取得する。添付には `gh pr create` / `gh pr edit` / `gh pr comment` の `--attach` を使う。

- `--attach '<path>#<alt text>'` の形式で指定する。複数添付はフラグを繰り返す
- 本文内で同じローカルパスを `![alt](./shot.png)` と参照すると、その箇所がアップロード先の URL に書き換わる。参照しない添付は本文末尾に追加される
- 動画をプレーヤー表示するには、参照だけの段落に置く
- リポジトリへの push 権限が必要

### PR初回作成時のデフォルト

draft (`--draft`) で作成し、assigneeとreviewerを指定しない。明示的な指示があったときだけopenで作成する。

reviewer の設定 (`--add-reviewer`) は、明示的に指示されたときだけ行う。draft でも依頼の通知は相手に届くため、文面から読み取りにくいときは設定前に確認する。CODEOWNERS 対象のパスを変える PR を open で作ると、code owner に review が自動で依頼される。動作確認用の PR ではそのパスを避けるか、作成前に確認する。

### PR更新時

PR番号は `gh pr view --json number -q '.number'` で確認する。ブランチ名から推測しない。更新前にユーザーへ確認を取る。

### failしたCIの修正

CI jobやworkflow自体を修正した場合のみ適用。通常のコード変更は localのtestで完結させる。修正をpushした後はCIをwatchし、failしたら通るまで対応する。

### PR上にcommentするとき

自分がClaude Codeであることをcommentに含める。

## git操作

### branch 作成時は twig を使う

branch を作成するときは worktree を使う。`git switch -c` や `git checkout -b` で直接 branch を切らない。

着手前に必ず `/twig:twig-guide` skill を読み、twig の操作を確認してから実装する。

twig で扱う主な操作:

- 新規 branch の worktree 作成
- 変更を別 branch へ移動 (carry)
- merged worktree の削除

理由:

- branch 切り替え時に stash が不要になる
- 複数 branch を並行して作業できる

### 作成した worktree を herdr の workspace に表示する

herdr の pane 内 (`HERDR_ENV=1`) で worktree を作ったら、続けて `herdr worktree open --path <worktree> --no-focus` を実行し、作成した worktree を現在の repository の workspace 配下に表示する。

- 作る手段を問わない。`twig add` のほか、repository の規則で指定された script や `git worktree add` で作った worktree も対象とする
- subagent に worktree を作らせるときは、作成直後に上の command を実行することを subagent への指示に含める。subagent は main session の文脈を引き継がないため、指示に無い手順は実行されない
- 指示に含め忘れたときや subagent の実行を確かめられないときは、main session が `git worktree list` で作成済みの worktree を確かめて登録する

### ステージするファイルはパスで指定する

`git add -A` や `git add .` を使わない。`git status --short` で対象を確認し、変更したファイルをパスで列挙して add する。

## multi-agent orchestration

Orca orchestration は worker を起動して結果を待ち受ける作業にだけ使う。着手前に `orca skills get orchestration` でバージョンが一致した guide を読む。

使う場合:

| ケース | 例 |
| --- | --- |
| 並列実行して全完了を待つ | 独立した3件を配り全 worker_done を待つ |
| 段階依存 (DAG) | 調査 → 設計 → 実装 → 検証で成果物を渡す |
| 承認を挟む | 設計案の時点で止め、判断してから実装へ進む |
| 監督が必要な長時間作業 | escalation や question に応答しながら実行する |

使わない場合:

| ケース | 代わりに使うもの |
| --- | --- |
| 投げっぱなしの委譲 | orca-cli の handoff |
| 単発の調査・検索 | 通常の subagent |
| terminal 起動や worktree 操作のみ | orca-cli |
| 観点ごとの決定論的な fan-out | Workflow tool |

worker には bypass 系のフラグを付けない。

## コード編集

### 実装作業のsubagent委譲（Fable 5のみ）

main sessionのmodelがFable 5のときのみ有効。それ以外のmodelでは通常どおり自分で実装する。

コードの実装作業（ファイル編集、commit、push、PR作成）は自分で直接行わず、`model: "opus"` を指定したsubagentに委譲する。

- 委譲するのは実装作業のみ。調査、設計、方針決定、subagentへの指示書作成はmain sessionで行う
- subagentには背景、変更内容、検証方法、完了条件を具体的に指示する
- PR作成を含む場合は github-pr-creator agent を `model: "opus"` で起動する

例外:

- commit と push だけの作業は main session が直接行う。判断の介在しない作業に subagent の起動コストが見合わない
- 資格情報の値を含むファイルは main session が Write で直接書く。値を含む指示文は auto mode の classifier が拒否する。subagent には、作成済みで編集不要・内容を出力しないことを伝える

理由:

- 実装品質の高い model に実装を任せる
- main sessionのcontextを調査・レビューに残せる

### advisor の呼び出し基準

system prompt の advisor 既定 (実質的な作業の前に毎回呼ぶ) を以下で上書きする。

原則として作業を終えてから一度だけ呼ぶ。着手前には呼ばない。

呼ぶケース。

- 作業が一通り完了し、成果物が揃った時点で 1 回 (実装完了後、PR 作成前、文書の完成時)
- 不可逆・高影響な操作の実行直前 (本番への適用、DB migration、破壊的操作)。調査と準備が済んだ段階で呼ぶ
- スタック時 (同じエラーの繰り返し、結果が仮説と矛盾、進展しない)

呼ばないケース。

- 着手前および方針決定の段階
- 次のアクションが tool 出力で一意に決まる反応的作業
- 確立済みパターンの踏襲、テストが即座に正否を判定する可逆変更
- 定型運用 (deps update、CI watch、conflict 解消)

頻度の目安は 1 タスクあたり 1 回。中間はスタック条件を満たしたときのみ。

理由:

- 着手前は会話に材料が無く、advisor が参照できる情報が自分とほぼ同じになるため、別視点としての利益が小さい
- 作業後は差分・調査結果・判断根拠が揃っており、レビュー対象として最も情報量が多い
- 判断が介在しない作業への呼び出しは計測すると価値が薄い

### テストコード修正時

- 修正したテストコードは必ず再実行して、テストが通ることを確認する
- テストが失敗したとき、テストが通るような変更を加えることは禁止

### markdown変更時

markdownlintの指摘事項に抵触しないようにmarkdownを変更する。

コードブロックを利用するときは必ず言語を指定:

```txt
hello world
```

### コメント記述ガイドライン

言語非依存の方針。語調・表記は「自然言語生成」に従う。

#### 自己完結を理想とする

コメントを他システム・他ファイル・CIジョブ名・定数値など、外部に存在する知識へ依存させない。対象の改名や廃止でコメントが陳腐化する。事実はそれが属する単一情報源に置く。

悪い例 (CIジョブ名に結合):

```go
// release-prod ジョブのタグ照合で参照する
const releaseTag = "stable"
```

良い例 (結合を断ち削除):

```go
const releaseTag = "stable"
```

結合をどうしても残す場合は次節に従う。

#### 意図的な相互参照は NOTE: を付ける

外部への結合を残す場合は `NOTE:` を付け、意図的な相互参照と分かるようにする。印が無い参照は、保守者が陳腐化したコメントと区別できない。

悪い例 (印が無く意図が伝わらない):

```go
// migration 0042 と列順を一致させる
var columns = []string{"id", "name", "email"}
```

良い例 (NOTE: で意図的と明示):

```go
// NOTE: migration 0042 と列順を一致させる
var columns = []string{"id", "name", "email"}
```

#### what ではなく why を書く

処理・型・シグネチャから読み取れることは説明しない。自明な struct field やゲッターにコメントを付けない。判断の理由や前提を書く。ここでの why はコードが現にそうなっている理由を指す。変更の経緯は含めない (次節)。

悪い例 (型から自明):

```go
// ユーザーのIDを返す
func (u User) ID() int { return u.id }
```

良い例 (why を書く):

```go
// 認証前は id が 0 になりうるため呼び出し側で検証する
func (u User) ID() int { return u.id }
```

#### 変更の経緯を書かない

why には 2 種類ある。コードが現にそうなっている理由と、今回の変更でそうした理由である。コメントに書くのは前者のみ。後者は commit message や PR description に書く。git が経緯の単一情報源であり、コメントに書くと重複になる。

判定基準: 変更の diff を知らない読者に意味が通るか。「以前は」「〜に変更」「〜を追加」「〜を修正」「レビュー指摘対応」など、変更前の状態や作業経緯を前提とする語が入るなら経緯である。

悪い例 (変更の経緯):

```go
// nil のとき panic していたためチェックを追加
if cfg == nil {
 return defaultConfig
}
```

良い例 (コードの前提のみ):

```go
// 設定ファイル未配置の環境では cfg は nil になる
if cfg == nil {
 return defaultConfig
}
```

経緯を取り除いて残る事実が無ければ、コメント自体を書かない。

#### 値や識別子を重複させない

他所で定義された値や識別子をコメントに書き写さない。定義が変わるとコメントだけ古くなる。

悪い例 (定義値の重複):

```go
// 上限は 30 秒
const maxTimeout = 30 * time.Second
```

良い例 (定義に語らせる):

```go
const maxTimeout = 30 * time.Second
```

この規則は値の書き写しを禁じるもので、コメントが説明している対象を伏せる規則ではない。直下の行にある引数・オプション・条件を説明するときは、その識別子を名指しする。対象を書かないと、コメントがどのコードの理由なのか読み手が判断できず、該当のコードを誤って消されやすくなる。

悪い例 (何についての理由か分からない):

```go
// 外部から任意に指定できるため、他ホストへは戻さない
redirectBack(w, r, Options{AllowOtherHost: false})
```

良い例 (対象のオプションを名指しする):

```go
// 外部から任意に指定できるため、他ホストへは戻さないよう AllowOtherHost: false を明示する
redirectBack(w, r, Options{AllowOtherHost: false})
```

#### 投機的な将来予測を書かない

「将来こう拡張できる」等の予測を書かない。実装され検証された事実だけを残す。

悪い例 (将来予測):

```go
// 将来は複数リージョンに拡張できる
func deploy(region string) error { return nil }
```

良い例 (現在の事実のみ):

```go
func deploy(region string) error { return nil }
```

#### 実装変更時に doc コメントを更新する

実装を変えたら doc コメントも更新し、実装と一致させる。古い説明は誤情報になる。

悪い例 (実装と不一致):

```go
// 結果を昇順で返す
func sorted() []int { return descending() }
```

良い例 (実装と一致):

```go
// 結果を降順で返す
func sorted() []int { return descending() }
```

#### 密度・語調は周囲のコードに合わせる

コメントの量と語調を周囲のコードに揃える。

悪い例 (周囲は無コメントなのに冗長):

```go
// 2つの整数を受け取り、その和を返す関数である
func add(a, b int) int { return a + b }
```

良い例 (周囲に合わせ省略):

```go
func add(a, b int) int { return a + b }
```

## ツール操作

### chrome mcp

Claude for Chrome MCPを利用するとき、一連のブラウザ操作をまとめて1つのsubagentに委譲すること。main sessionのcontextを節約するため。

注意:

- chrome操作以外の処理を同じsubagentに依頼しないこと

### cli

rmを使うときは-fを使うこと。

理由: rmのみの場合、対話的な実行になり、実行できないため

### JSON parse

JSONのパース・フィルタリングにはjqを使うこと。pythonのワンライナーは使わない。

必ず `-c` (compact output) を付けること。意味の解釈が目的のときは `@tsv` を使うこと。

理由:

- jqの方が簡潔で可読性が高い
- pythonは自由度が高すぎるため処理を制限する
- `-c` で改行・インデントを除去しトークン数を削減
- `@tsv` は構造情報を落として値だけ出力するため内容を読んで判断する用途でさらにトークン効率が良い

### sleep

sleepの時間をバックオフしないこと。常に短い時間を適用して、確認したい事項に変動があるまで繰り返し実行すること
