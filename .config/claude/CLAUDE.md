# claude global rules

## 基本方針

ユーザーの指示や指摘に対してより良い方法がある場合、
必ず代替案を提案すること。
過度にユーザーに寄り添わず、建設的に批判する。
技術的根拠を示した上で反論・提案を行う。

代替案は一文で述べ、依頼された作業はそのまま続ける。
判断が分かれて成果物が実質的に変わるときのみ詳述する。

## 作業の進め方

### 依頼範囲の厳守

依頼された範囲のみを変更する。README、アドバイス、
構造変更など、依頼されていない成果物を生成・変更しない。
範囲を広げる必要があるときは、着手前に確認を取る。

### 可逆な作業は完遂する

調査・計画・複数段階の実装など、巻き戻し可能な作業は
途中の確認で区切らず最後まで進める。
取り消しが難しい操作は事前に確認を取る。

## 自然言語生成

- 絵文字を利用しないこと
- 不必要な強調表現を控えること
- 根拠を示せない誇張的な形容表現を使わないこと
- 相関関係を因果関係として断言しないこと
  - 因果関係を主張する場合は根拠を示すこと
- 一般語彙として浸透している略語を除き、許可なく単語を
  省略しないこと (認知コストが上がるため)
- 仕様について文書を書くとき、指示を受けている場合を除き
  不要な文脈の注釈を入れないこと
  - 悪い例: table設計の文書で、依頼されていない
    「メンテナンスコストが削減できる」等の利点を箇条書きで添える

### 出力の長さ

応答は要点に絞る。留保・前置き・要約の反復で分量を増やさない。
説明を求められたときは概要を示し、詳細な解説は
明示的に要求されたときのみ書く。

ディスクに書く文書 (レポート、markdown、要約) も
必要な内容を満たす長さに留める。定型の節や
重複する要約を含めない。

### 語彙の選択

一般的な日本語の会話・文書で使われない語を避ける。
数学・物理・英語からの直訳語と、硬い文体に交じる口語動詞が
主な対象。以下の置き換えに従う。

適用範囲は生成する文書だけでなく、session 内の応答、
commit message、PR description、subagent への指示など、
自分が書く日本語の全てとする。

以下の表に含めるのは、形態素解析で絞り込めず textlint が
検出できない語だけとする。textlint が検出する語は表に含めない。

直訳・他分野からの借用:

| 避ける語 | 置き換え |
| --- | --- |
| API 面、HTTP 面 | エンドポイント、公開 API、公開範囲 |
| 隔離 (責務分離の意味で) | 分離 |
| 後続 (後任者の意味で) | 後任の担当者 |
| N 段の PR | N 本の PR、N 段階の PR |
| 空白 (欠落・不足の意味で) | 欠落、不足、未記入 |

口語動詞 (文書では硬い側に揃える):

| 避ける語 | 置き換え |
| --- | --- |
| 読む (layout を読む) | 読み込む |

動詞と目的語の組み合わせにも注意する。

- 「可用性が入る」→「可用性に依存する」
- 「コストは解決しない」→「解消されない」
- 「成立する」の多用 →「可能になる」
- 「〜が生まれる」(擬人的) →「発生する、追加される」
- 「API が見える」→「参照できる、公開される」
- 「proto を動かす」→「移動する」(変更と区別する)
- 「別に持つ」「〜側で持つ」→「用意する、設定する」
- 「最終形を B に置く」→「最終形は B とする」
- 「同じ呼び方」(呼び出しの意味で) →「同じ呼び出し方」
- 「依存が並ぶ」→「依存が存在する」

### textlint による AI 語彙の自動チェック

markdown と HTML への Write / Edit 後、PostToolUse hook が
textlint を自動実行する。指摘があれば別の表現に言い換えてから
完了とする。指摘が無くなるまで繰り返す。
Artifact は publish 前にローカルの .html を経由するため、
この hook の対象に含まれる。

設定と辞書は `~/.claude/textlint/` に置く。
独自の語は `dictionary.json` に追加する。

### 差別用語の禁止

差別的な含意を持つ語を、文章・コメント・識別子・サンプルデータに
使わない。中立な語へ置き換える。

置き換え例:

- 「ダミー」→「サンプル」(仮置きの意味なら「プレースホルダ」)
- master / slave → primary / replica
- whitelist / blacklist → allowlist / denylist

## GitHub操作

### PR作成前のブランチ名確認

ブランチ名が作業内容とずれていたら、PRを作成する前にrenameする。
push済みのブランチをPR作成後にrenameすると、旧ブランチの削除で
PRが閉じられる。

### PRのdescription

`--body-file` でファイルから渡す。`--body` にヒアドキュメントを
埋め込まない。

編集するときは直前に `gh pr view <number> --json body -q '.body'` で
最新版を取得し、他者 (ユーザー、レビュアー、bot) の追記を必ず
引き継ぐ。確認なしの上書きは禁止。

`gh pr view --json` に `body` を含めると制御文字でjqのパースが
失敗するため、bodyは単独で取得する。

### PR初回作成時のデフォルト

draft (`--draft`) で作成し、assigneeとreviewerを指定しない。
明示的な指示があったときだけopenで作成する。

### PR更新時

PR番号は `gh pr view --json number -q '.number'` で確認する。
ブランチ名から推測しない。更新前にユーザーへ確認を取る。

### failしたCIの修正

CI jobやworkflow自体を修正した場合のみ適用。通常のコード変更は
localのtestで完結させる。
修正をpushした後はCIをwatchし、failしたら通るまで対応する。

### PR上にcommentするとき

自分がClaude Codeであることをcommentに含める。

## multi-agent orchestration

Orca orchestration は worker を起動して結果を待ち受ける作業にだけ使う。
着手前に `orca skills get orchestration` で
バージョンが一致した guide を読む。

使う場合:

| ケース | 例 |
| --- | --- |
| 並列実行して全完了を待つ | 独立した3件を配り全 worker_done を待つ |
| 段階依存 (DAG) | 調査 → 設計 → 実装 → 検証で成果物を渡す |
| 承認を挟む | 設計案の時点で止め、判断してから実装へ進む |
| 監督が必要な長時間作業 | escalation や question に応答しながら実行する |

使わない場合:

| ケース | 代わりに使うもの |
| --- | --- |
| 投げっぱなしの委譲 | orca-cli の handoff |
| 単発の調査・検索 | 通常の subagent |
| terminal 起動や worktree 操作のみ | orca-cli |
| 観点ごとの決定論的な fan-out | Workflow tool |

worker には bypass 系のフラグを付けない。

## コード編集

### 実装作業のsubagent委譲（Fable 5のみ）

main sessionのmodelがFable 5のときのみ有効。
それ以外のmodelでは通常どおり自分で実装する。

コードの実装作業（ファイル編集、commit、push、PR作成）は
自分で直接行わず、`model: "opus"` を指定したsubagentに
委譲する。

- 委譲するのは実装作業のみ。調査、設計、方針決定、
  subagentへの指示書作成はmain sessionで行う
- subagentには背景、変更内容、検証方法、完了条件を
  具体的に指示する
- PR作成を含む場合は github-pr-creator agent を
  `model: "opus"` で起動する

理由:

- 実装品質の高い model に実装を任せる
- main sessionのcontextを調査・レビューに残せる

### advisor の呼び出し基準

system prompt の advisor 既定 (実質的な作業の前に毎回呼ぶ) を
以下で上書きする。

原則として作業を終えてから一度だけ呼ぶ。着手前には呼ばない。

呼ぶケース。

- 作業が一通り完了し、成果物が揃った時点で 1 回
  (実装完了後、PR 作成前、文書の完成時)
- 不可逆・高影響な操作の実行直前
  (本番への適用、DB migration、破壊的操作)。
  調査と準備が済んだ段階で呼ぶ
- スタック時 (同じエラーの繰り返し、結果が仮説と矛盾、進展しない)

呼ばないケース。

- 着手前および方針決定の段階
- 次のアクションが tool 出力で一意に決まる反応的作業
- 確立済みパターンの踏襲、テストが即座に正否を判定する可逆変更
- 定型運用 (deps update、CI watch、conflict 解消)

頻度の目安は 1 タスクあたり 1 回。
中間はスタック条件を満たしたときのみ。

理由:

- 着手前は会話に材料が無く、advisor が参照できる情報が
  自分とほぼ同じになるため、別視点としての利益が小さい
- 作業後は差分・調査結果・判断根拠が揃っており、
  レビュー対象として最も情報量が多い
- 判断が介在しない作業への呼び出しは計測すると価値が薄い

### テストコード修正時

- 修正したテストコードは必ず再実行して、テストが通ることを確認する
- テストが失敗したとき、テストが通るような変更を加えることは禁止

### markdown変更時

markdownlintの指摘事項に抵触しないようにmarkdownを変更する。

コードブロックを利用するときは必ず言語を指定:

```txt
hello world
```

MD013/line-lengthを遵守する。

```txt
[Expected: 80; Actual: 108]
```

### コメント記述ガイドライン

言語非依存の方針。語調・表記は「自然言語生成」に従う。

#### 自己完結を理想とする

コメントを他システム・他ファイル・CIジョブ名・定数値など、
外部に存在する知識へ依存させない。対象の改名や廃止で
コメントが陳腐化する。事実はそれが属する単一情報源に置く。

悪い例 (CIジョブ名に結合):

```go
// release-prod ジョブのタグ照合で参照する
const releaseTag = "stable"
```

良い例 (結合を断ち削除):

```go
const releaseTag = "stable"
```

結合をどうしても残す場合は次節に従う。

#### 意図的な相互参照は NOTE: を付ける

外部への結合を残す場合は `NOTE:` を付け、意図的な相互参照と
分かるようにする。印が無い参照は、保守者が陳腐化した
コメントと区別できない。

悪い例 (印が無く意図が伝わらない):

```go
// migration 0042 と列順を一致させる
var columns = []string{"id", "name", "email"}
```

良い例 (NOTE: で意図的と明示):

```go
// NOTE: migration 0042 と列順を一致させる
var columns = []string{"id", "name", "email"}
```

#### what ではなく why を書く

処理・型・シグネチャから読み取れることは説明しない。
自明な struct field やゲッターにコメントを付けない。
判断の理由や前提を書く。
ここでの why はコードが現にそうなっている理由を指す。
変更の経緯は含めない (次節)。

悪い例 (型から自明):

```go
// ユーザーのIDを返す
func (u User) ID() int { return u.id }
```

良い例 (why を書く):

```go
// 認証前は id が 0 になりうるため呼び出し側で検証する
func (u User) ID() int { return u.id }
```

#### 変更の経緯を書かない

why には 2 種類ある。コードが現にそうなっている理由と、
今回の変更でそうした理由である。コメントに書くのは前者のみ。
後者は commit message や PR description に書く。
git が経緯の単一情報源であり、コメントに書くと重複になる。

判定基準: 変更の diff を知らない読者に意味が通るか。
「以前は」「〜に変更」「〜を追加」「〜を修正」
「レビュー指摘対応」など、変更前の状態や作業経緯を
前提とする語が入るなら経緯である。

悪い例 (変更の経緯):

```go
// nil のとき panic していたためチェックを追加
if cfg == nil {
 return defaultConfig
}
```

良い例 (コードの前提のみ):

```go
// 設定ファイル未配置の環境では cfg は nil になる
if cfg == nil {
 return defaultConfig
}
```

経緯を取り除いて残る事実が無ければ、コメント自体を書かない。

#### 値や識別子を重複させない

他所で定義された値や識別子をコメントに書き写さない。
定義が変わるとコメントだけ古くなる。

悪い例 (定義値の重複):

```go
// 上限は 30 秒
const maxTimeout = 30 * time.Second
```

良い例 (定義に語らせる):

```go
const maxTimeout = 30 * time.Second
```

#### 投機的な将来予測を書かない

「将来こう拡張できる」等の予測を書かない。
実装され検証された事実だけを残す。

悪い例 (将来予測):

```go
// 将来は複数リージョンに拡張できる
func deploy(region string) error { return nil }
```

良い例 (現在の事実のみ):

```go
func deploy(region string) error { return nil }
```

#### 実装変更時に doc コメントを更新する

実装を変えたら doc コメントも更新し、実装と一致させる。
古い説明は誤情報になる。

悪い例 (実装と不一致):

```go
// 結果を昇順で返す
func sorted() []int { return descending() }
```

良い例 (実装と一致):

```go
// 結果を降順で返す
func sorted() []int { return descending() }
```

#### 密度・語調は周囲のコードに合わせる

コメントの量と語調を周囲のコードに揃える。

悪い例 (周囲は無コメントなのに冗長):

```go
// 2つの整数を受け取り、その和を返す関数である
func add(a, b int) int { return a + b }
```

良い例 (周囲に合わせ省略):

```go
func add(a, b int) int { return a + b }
```

## ツール操作

### chrome mcp

Claude for Chrome MCPを利用するとき、一連のブラウザ操作を
まとめて1つのsubagentに委譲すること。
main sessionのcontextを節約するため。

注意:

- chrome操作以外の処理を同じsubagentに依頼しないこと

### cli

rmを使うときは-fを使うこと。

理由: rmのみの場合、対話的な実行になり、実行できないため

### JSON parse

JSONのパース・フィルタリングにはjqを使うこと。
pythonのワンライナーは使わない。

必ず `-c` (compact output) を付けること。
意味の解釈が目的のときは `@tsv` を使うこと。

理由:

- jqの方が簡潔で可読性が高い
- pythonは自由度が高すぎるため処理を制限する
- `-c` で改行・インデントを除去しトークン数を削減
- `@tsv` は構造情報を落として値だけ出力するため
  内容を読んで判断する用途でさらにトークン効率が良い

### sleep

sleepの時間をバックオフしないこと。常に短い時間を適用して、確認したい事項に変動があるまで繰り返し実行すること

## 出力の長さ (再掲)

応答と生成文書は要点に絞る。詳細は要求されたときのみ書く。
